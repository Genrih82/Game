1. Рубильник блокировки на главном экране не спрашивает PIN
Уверенность: подтверждено.

Место: HomeScreen, переключатель; MainViewModel.setLockEnabled.

Доказательство. Кнопка «Настройки» при существующем PIN идёт в settings_pin. Переключатель «Блокировка после сна» вызывает setLockEnabled сразу.

MainActivity.kt, строки 74–76:

                onOpenSettings = {
                    if (vm.uiState.hasParentPin) navController.navigate("settings_pin") else navController.navigate("settings")
                },

MainViewModel.kt, строки 104–106:

    fun setLockEnabled(enabled: Boolean) {
        saveProfile(uiState.profile.copy(lockEnabled = enabled))
    }

saveProfile пишет lockEnabled = false, затем останавливает LockMonitorService. shouldPresentLock после этого сразу возвращает false.

Условие. Ребёнок открывает LearnLock в свободном интервале, либо добирается до главного экрана, пока задание не на переднем плане. PIN не нужен.

Состояние. До: lockEnabled = true, сервис жив, alarm может стоять. После: lockEnabled = false, сервис остановлен, tasksSolved и failedAttempts этим вызовом не трогаются, но planNextLaunch всё равно переписывает nextLaunchAtMillis на «сейчас + интервал» и обнуляет tasksSolved. LockActivity сама не закрывается. Следующий опрос задание уже не покажет.

Последствие. Ребёнок выключает блокировку без родителя. PIN и профиль в Room остаются.

Исправление. Пока hasParentPin истинно, не вызывать setLockEnabled с главного экрана: тот же verifyParentPin, что открывает settings_pin, и только после valid писать lockEnabled.


2. Открытие приложения при уже наступившем запуске выдаёт интервал без заданий
Уверенность: подтверждено.

Место: MainViewModel.bootstrap, вход на маршрут settings, LearnLockRepository.refreshNextLaunchIfExpired.

Доказательство. При создании MainActivity и при каждом входе в настройки вызывается обновление. Если nextLaunchAtMillis равен 0 или уже наступил, это полный scheduleNextLaunch.

MainViewModel.kt, строки 41–45:

        viewModelScope.launch {
            repository.ensureDefaults()
            repository.refreshNextLaunchIfExpired()
            LockController.scheduleNextLaunch(getApplication())

MainActivity.kt, строки 150–151:

        composable("settings") {
            LaunchedEffect(Unit) { vm.refreshNextLaunchIfExpired() }

LearnLockRepository.kt, строки 95–99:

    suspend fun refreshNextLaunchIfExpired() {
        val session = sessionStore.state.first()
        if (session.nextLaunchAtMillis == 0L || session.nextLaunchAtMillis <= System.currentTimeMillis()) {
            scheduleNextLaunch()
        }
    }

scheduleNextLaunch пишет nextLaunchAtMillis = now + launchIntervalMinutes (не меньше 5), tasksSolved = 0, consecutiveWrong = 0. Будущее время эта функция не сдвигает: при простом открытии настроек, пока запуск ещё впереди, условие ложно и запись не делается.

Условие. Блокировка включена, срок запуска уже наступил, создаётся MainActivity (иконка, уведомление сервиса с intent на MainActivity, гибель процесса и новый заход). Тот же сдвиг делает вход в settings, если срок уже прошёл; до экрана настроек нужен PIN.

Состояние. До: nextLaunchAtMillis <= now, tasksSolved может быть 1…N−1, LockActivity может быть жива. После: nextLaunchAtMillis в будущем, tasksSolved = 0, LockController.scheduleNextLaunch ставит alarm на новое время, shouldPresentLock становится false. failedAttempts и lockedUntilMillis не меняются.

Последствие. Серия ответов стирается, телефон получает целый интервал без tasksToUnlock верных ответов. Если LockActivity.load ещё не прочитал сессию, он видит isSessionActive и сам закрывает задание через 1,1 с.

Исправление. Убрать refreshNextLaunchIfExpired из bootstrap и из LaunchedEffect маршрута settings. Новый nextLaunchAtMillis писать только после набора tasksToUnlock, родительского PIN и явного сохранения интервала.

nextLaunchAtMillis здесь не пишется. Контроллер читает старое значение и при прошлом или нулевом сроке выходит, не вызывая AlarmManager.

Исправление. В parentUnlock после успешного unlockWithParentPin вызвать repository.scheduleNextLaunch, дождаться записи и только затем LockController.scheduleNextLaunch, как в ветке полной серии.


4. Повторный показ не поднимает уже остановленную LockActivity
Уверенность: подтверждено по коду. Что конкретная прошивка уничтожает activity по Home, на устройстве не проверялось.

Место: LockController.presentLock, LockActivity.onDestroy.

Доказательство. Флаг ставится до startActivity и снимается только в onDestroy. Повторный presentLock при живом флаге не вызывает startActivity.

LockController.kt, строки 87–88:

    fun presentLock(context: Context, forcePreview: Boolean = false) {
        if (!forcePreview && !lockVisible.compareAndSet(false, true)) return

LockActivity.kt, строки 23–26:

    override fun onDestroy() {
        LockController.onLockActivityClosed()
        super.onDestroy()
    }

onLockActivityClosed обнуляет и lockVisible, и launchNotificationShown. Accessibility, опрос раз в 15 с и SCREEN_ON все идут в presentLock. Пока activity только остановлена (обычный Home: onStop без onDestroy), флаг остаётся true, и эти вызовы ничего не поднимают.

Условие. Задание показано, nextLaunchAtMillis всё ещё просрочен, ребёнок уходит Home или в другое приложение, процесс не убивает LockActivity.

Состояние. До ухода: LockActivity на экране, lockVisible = true, срок просрочен, tasksSolved как был. После ухода: activity жива в фоне, флаг true, alarm не переставляется, опрос и Accessibility не вызывают startActivity. После настоящего onDestroy: оба флага false; если срок всё ещё просрочен, ближайший опрос откроет задание снова.

Последствие. Телефон остаётся свободным, хотя серия не добрана. Это ломает собственный возврат к заданию. Обходы из docs/BYPASS_NOTES.md (Safe Mode, force-stop, второй пользователь) сюда не относятся.

Исправление. Если LockActivity ещё жива, повторный presentLock должен всё равно вызывать startActivity с уже стоящими FLAG_ACTIVITY_NEW_TASK | CLEAR_TOP | SINGLE_TOP, чтобы singleTask поднял тот же экземпляр. Сбрасывать lockVisible по-прежнему в onDestroy.

5. Любое сохранение профиля и смена PIN начинают интервал заново
Уверенность: подтверждено.

Место: MainViewModel.planNextLaunch, его вызывают saveProfile и setPin.

Доказательство. scheduleNextLaunch не смотрит, был ли прежний срок в будущем и менялся ли интервал.

MainViewModel.kt, строки 117–119:

        repository.scheduleNextLaunch(profile)
        LockController.scheduleNextLaunch(getApplication())

LearnLockRepository.kt, строки 85–92:

        val currentProfile = profile ?: getProfileOrDefault()

            TimeUnit.MINUTES.toMillis(intervalMinutes.toLong())

Условие. Родитель сохраняет настройки или меняет PIN. Достаточно смены имени или цвета. Сюда же попадает переключатель с главного экрана.

Исправление. Не вызывать scheduleNextLaunch из сохранения, если launchIntervalMinutes не изменился и записанный nextLaunchAtMillis ещё в будущем. Обнулять tasksSolved только в ветке, которая закрывает набранную серию или принимает родительский PIN.

8. Окно 7:00–21:00 на показ не влияет
Уверенность: подтверждено. Это расхождение контракта, не догадка.

Место: LearnLockRepository.shouldPresentLock и неиспользуемый outsideWindowDecision.

Доказательство. KDoc обещает отказ вне окна в режиме NO_TASKS. Тело метода смотрит только lockEnabled и nextLaunchAtMillis. outsideWindowDecision в проекте никем не вызывается. Экран настроек при этом сохраняет часы и режимы «Без задач» / «Полный запрет».

LearnLockRepository.kt, строки 111–122:

     * Условия отказа: блокировка выключена, сессия ещё активна,
     * либо сейчас вне окна и режим [OutsideWindowMode.NO_TASKS].
     */
    suspend fun shouldPresentLock(): Boolean {
        val profile = getProfileOrDefault()
        if (!profile.lockEnabled) return false
        val session = sessionStore.state.first()
        return session.nextLaunchAtMillis == 0L || session.nextLaunchAtMillis <= System.currentTimeMillis()
    }

Условие. Любой час суток, в том числе до 7:00 и после 21:00, при включённой блокировке и наступившем nextLaunchAtMillis.

Последствие. Родитель выставляет «Без задач» и всё равно получает задание. Правило совместимости как раз описывает текущий код: показ режут выключенная блокировка и будущий срок. Расходится KDoc, настройки, docs/BETA_TEST.md (сценарий 7) и комментарий в Models.kt.

Исправление. Не подключать outsideWindowDecision к shouldPresentLock без отдельного согласия на смену контракта. Поправить KDoc так, чтобы он описывал два фактических условия, и не обещать на экране настроек режим, который код не читает.

10. Выключение блокировки не снимает alarm, и receiver снова поднимает сервис
Уверенность: подтверждено. Сработает ли pending alarm после Doze, на устройстве не проверялось.

LaunchAlarmReceiver.kt, строки 18–23:

                LockController.startMonitoring(appContext)

Место: AppDatabase.create.

Доказательство. Версия 6. Подключены миграции 2→3, 3→4, 4→5, 5→6 и fallbackToDestructiveMigration().

Что миграции делают с уже существующей строкой:

- 2→3 добавляет backgroundColor со значением 0. PIN не трогает.
- 3→4 добавляет launchIntervalMinutes и accessDurationMinutes с временным default 5, затем копирует в обе колонки sessionMinutes. Интервал не обнуляется. PIN не трогает.
- 4→5 добавляет failedAttempts = 0 и lockedUntilMillis = 0. pinHash и salt не переписываются.
- 5→6 добавляет tasksToUnlock со значением 10. Интервал и PIN остаются.

Колонки окна, категорий, lockEnabled и skillTag в этих ALTER нет. Их наличие в version 2 по репозиторию не проверить: exportSchema = false, исходного CREATE TABLE нет. Если после цепочки схема не совпадёт с entity, Room падает на проверке. Зарегистрированная, но неудачная миграция сама по себе базу не уничтожает.

Fallback срабатывает, когда пути нет: version 1 и любая версия вне 2…6. Тогда файл learnlock.db создаётся заново, профиль и PIN пропадают.

Условие для уже установленной version 6 ложно: номер версии тот же, миграция и fallback не запускаются.

Исправление. Удалить fallbackToDestructiveMigration(), чтобы неизвестная версия останавливала открытие базы, а не создавала пустую.


Трассы без дефекта в самом сценарии
===================================

Граница модулей. Показ решает только shouldPresentLock. Срок считает только LearnLockRepository.scheduleNextLaunch. LockController.scheduleNextLaunch лишь читает уже записанный millis и ставит alarm, request code 1002. Экран открывает presentLock. UI не обращается к DAO, DataStore и PinHasher. Генерация из приложения идёт через TaskEngine.nextTask. isSessionActive читает тот же nextLaunchAtMillis, второго правила показа в живом коде нет. outsideWindowDecision к показу не подключён: это дефект 8, не вторая рабочая политика.

Первый запуск. ensureDefaults создаёт профиль с lockEnabled = false, если строки нет. PIN нет, кнопка ведёт в онбординг, затем pin_setup, затем permissions_first, затем settings. setParentPin пишет PBKDF2: pinHash и salt, открытый PIN в базу не попадает. Первый nextLaunchAtMillis появляется ещё до включения блокировки, потому что bootstrap видит 0. Включение переключателя вызывает planNextLaunch ещё раз: срок становится «сейчас + интервал», сервис стартует, alarm ставится. До включения shouldPresentLock false. Это тот же переключатель, что в дефекте 1, и то же обнуление серии, что в дефекте 5.

Верный ответ, порог ещё не взят. До: срок просрочен, tasksSolved = k, LockActivity жива, lockVisible = true. onCorrectAnswer пишет k+1, consecutiveWrong = 0, попытку в task_attempt. scheduleNextLaunch не вызывается, alarm не двигается. Экран остаётся, показывается следующая задача.

Верный ответ, порог взят. onCorrectAnswer доводит счётчик, затем репозиторий записывает новый nextLaunchAtMillis и ставит tasksSolved = 0, и только после этого контроллер читает срок и ставит alarm. Экран 1,1 с показывает разблокировку и закрывается, onDestroy сбрасывает флаги. shouldPresentLock false, немедленного повтора нет.

Неверный ответ. tasksSolved не уменьшается. consecutiveWrong растёт на 1. Пауза в ViewModel — две секунды. Новая задача запрашивается после неё. nextLaunchAtMillis и alarm не меняются. LockActivity остаётся.

PIN. Три неверных: failedAttempts становится 1, затем 2, на третьем пишется 0 и lockedUntilMillis = now + 30 с. Четвёртая попытка, пока срок не вышел, возвращает valid = false и счётчик не увеличивает, даже если цифры верные. После 30 с верный PIN обнуляет failedAttempts и lockedUntilMillis. Смена PIN идёт маршрутом change_pin и возвращает в settings; новый хеш и соль заменяют старые, профиль ребёнка не удаляется. Сброс вызывает только parentAuthDao.delete() и уводит в onboarding. Вход в настройки с главного экрана при уже существующем PIN идёт через settings_pin. До конца bootstrap кнопка показывает «Начать настройку», а не «Настройки». На экране задания при блокировке PIN текст всегда «Неверный PIN», но verifyParentPin ввод всё равно отвергает. Гипотеза, на устройстве не проверялась: восстановленный back stack сразу на settings PIN повторно не спросит.

Показ поверх уже открытого задания. Второй presentLock без force_preview выходит по lockVisible. Двух activity из-за этого нет. После честного finish успешной серии флаги сбрасываются, и задание в ту же секунду не возвращается, потому что срок уже в будущем. Повтор после ухода Home — это дефект 4, не эта ветка.

Accessibility. Свои окна (packageName) выходят до shouldPresentLock. Контакты и SMS из списка тоже, и до срока, и после: так написано в сервисе, это не обещание полного запрета. Любое другое приложение до срока не открывает задание. После срока вызывает presentLock. exported="true" стоит вместе с BIND_ACCESSIBILITY_SERVICE. canRetrieveWindowContent="false".

task-engine. Пустой набор категорий движок отвергает. Возраст 4 или 17 сужается до 5…16, ошибкой не считается. Навыка без category в SkillTag нет. Тесты проверяют генерацию математики, чтения и логики и совпадение ответа после нормализации регистра и пробелов.


Без телефона это не подтверждается
==================================

- Samsung, Xiaomi и Huawei: автозапуск, убийство LockActivity по Home, ограничение Accessibility. В коде только текст на экране прав.
- Выдан ли exact alarm и насколько setAndAllowWhileIdle уезжает в Doze.
- Полноэкранный intent при USE_FULL_SCREEN_INTENT и показ уведомления без выданного POST_NOTIFICATIONS. Падает ли notify и пропускает ли из-за этого один presentLock, по платформе вероятно, на этом аппарате не видно.
- Реальные обходы из docs/BYPASS_NOTES.md: Safe Mode, второй пользователь, force-stop, ADB, удаление. Код абсолютную блокировку не обещает, эти пути багом не считаются.
- Доходит ли манифестный SCREEN_ON на API 26+. Динамический receiver зарегистрирован только внутри живого сервиса.
- Успевает ли нажатие переключателя раньше первой строки профиля из Room.

Эту сборку можно ставить поверх уже установленной version 6: номер Room тот же, миграция и destructive fallback не запускаются, профиль и PIN из-за обновления схемы не пропадают. Блокирующего дефекта такой установки нет.
